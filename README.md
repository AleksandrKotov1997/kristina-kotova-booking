# Kristina Kotova Booking

Персональный сайт Kristina Kotova Lash & Brow Studio с онлайн-записью.
Проект собирается поэтапно по ТЗ: публичный сайт, услуги и работы из базы,
запись и закрытый кабинет мастера.

## Стек

Next.js App Router, React, TypeScript, Ant Design, CSS Modules,
TanStack Query, Axios, React Hook Form и Zod. Для критичной бизнес-логики
предусмотрены Vitest и React Testing Library. База каталога — Supabase; авторизация мастера добавляется на своём этапе.

## Локальный запуск

Нужны Node.js 20.9+ и pnpm.

```bash
pnpm install --frozen-lockfile
pnpm dev
```

Сайт открывается на http://localhost:3000. Для услуг, галереи и расписания нужны настройки
Supabase из `.env.example`. Значения хранятся в `.env.local` и не попадают в Git.

```bash
pnpm lint
pnpm typecheck
pnpm build
pnpm start
```

## Архитектура

- `src/app` — маршруты, layout и Route Handlers. Страницы подключают views.
- `src/views` — композиция конкретных экранов.
- `src/components` — общие компоненты и публичный AppLayout.
- `src/features` — логика фич: model, api, hooks.
- `src/shared` — общая инфраструктура, включая Axios-клиенты и форматирование.
- `src/server` — серверные запросы и преобразование данных базы.
- `supabase` — конфигурация CLI, миграции и начальный каталог.
- `src/app/globals.css` — дизайн-токены; локальные стили — в CSS Modules.

Такое разделение повторяет принцип архитектурного референса,
а backend остаётся внутри Next.js.

## Завершённые этапы

Публичный Header для desktop: логотип со ссылкой на главную, бренд,
шесть пунктов навигации, активная страница и кнопка записи. Общая разметка
рендерится на сервере; клиентским остаётся определение активного маршрута.
Шрифты Nunito и DM Serif Display подключены через `next/font`,
стили Ant Design включены в серверный HTML через AntdRegistry.
ESLint запрещает `any` и приведение типов через `as`/угловые скобки.

Hero главной страницы для desktop: заголовок с акцентной строкой, описание,
ссылки на `/booking` и `/services`, статистика и визуальный блок по макету.
`HomeView` собирает экран, `HomeHero` отвечает за первый блок,
`HomeHeroVisual` — за фото и декоративные карточки. Общие `ActionLink`
и `PageContainer` используются и в Header. Цвета, градиенты, типографика
и размеры заданы через дизайн-токены. Шрифт русского заголовка задан
отдельно через `--font-heading` (Times New Roman), поскольку
DM Serif Display не содержит кириллицу.

Контент Hero статический и взят из ТЗ и макета; API и база здесь не нужны.
Photo placeholder предусмотрен ТЗ на этапе разработки и должен быть
заменён реальным фото до production. Статистика и карточка «10 лет
в красоте» перенесены из макета, без вычислений на клиенте.

Все desktop-блоки главной собраны: Header, Hero, услуги, работы, о мастере,
контакты и footer. Ссылка `/#contacts` ведёт к блоку контактов.
Страницы `/works` и `/about` добавляются после приёмки главной;
`/services` и `/booking` пока содержат только базовые экраны. Полный каталог
и сценарий записи реализуются на своих этапах. Мобильная адаптация
предусмотрена после завершения desktop-версии.

Текущий статус и оставшиеся этапы: [docs/implementation-status.md](docs/implementation-status.md).

## Каталог услуг и Supabase

Блок «Услуги» на главной получает активный каталог через Next.js API.
Начальные 6 услуг для ресниц и 4 услуги для бровей взяты из согласованного
макета Figma и находятся в `supabase/seed.sql`.

Для локального сайта создайте `.env.local` по примеру `.env.example`:

- `SUPABASE_URL` — URL облачного проекта.
- `SUPABASE_PUBLISHABLE_KEY` — publishable key из Settings → API Keys.

Переменные читает только серверный клиент. Для чтения каталога используется
Supabase Data API через Axios с ролью anon и защитой RLS; secret key и
service_role для этого не нужны. Без настроенного окружения API возвращает
503, а интерфейс предлагает повторить запрос. Подмены каталога статическими
данными нет.

`GET /api/services` возвращает `{ data: Service[] }`.
Параметр `category=lashes` или `category=brows` фильтрует категорию;
без параметра возвращаются обе. Неизвестные параметры, повторная category
и неизвестная категория возвращают 400. Цена передаётся числом в рублях,
длительность — в минутах. Поля API используют camelCase, таблица — snake_case.
API и политика RLS разрешают чтение только активных услуг. Посетители
не могут добавлять, изменять или удалять услуги.

`sortOrder` хранит порядок карточек. Изменения названий, цен, описаний,
длительности и активности в базе отображаются без изменения кода сайта.
Кэш TanStack Query сохраняет каталог категории на 60 секунд; следующий
запрос после устаревания кэша получает актуальные данные. Ответ API не
кэшируется сервером.

`ServiceCard` и `SectionHeading` — общие компоненты.
`HomeServicesPreview` управляет выбранной категорией и состояниями запроса,
`features/services` содержит контракт, API-клиент и хук.
`server/services` содержит запрос базы, проверку ответа и преобразование
записи; Route Handler отвечает за HTTP и проверку параметров.
Ссылка карточки передаёт `serviceId` в `/booking`; обработка выбора
и полный сценарий записи реализуются на этапе Booking.

### Миграции

Версия Supabase CLI зафиксирована в devDependencies. Схема находится
в `supabase/migrations`; изменения схемы оформляются новой миграцией,
а не ручной правкой облачной таблицы.

```bash
pnpm supabase login
pnpm supabase link --project-ref YOUR_PROJECT_REF
pnpm supabase db push
pnpm supabase db query --linked --file supabase/seed.sql
```

Seed добавляет согласованный начальный каталог. Повторное применение
не перезаписывает уже существующие услуги: обновления каталога в MVP
делаются в Supabase Table Editor. Не меняйте id услуги — на него будет
ссылаться запись клиента. Отключение услуги делается через is_active.
Секреты, пароль базы и токен CLI не должны попадать в Git.

Проверка ограничений и RLS выполняется в транзакции с откатом,
поэтому тестовые записи не сохраняются:

```bash
pnpm supabase db query --linked --file supabase/tests/services.sql
```

## Галерея работ на главной

Блок «Работы» получает первые восемь активных записей через API.
Карточки и просмотр фотографий находятся в общих компонентах GalleryImageCard
и WorkGallery. Просмотр Ant Design поддерживает стрелки, Escape, счётчик,
масштабирование и возврат фокуса. Предусмотрены загрузка, ошибка с повтором,
пустой список и недоступное отдельное изображение.

GET /api/gallery возвращает { data: GalleryImage[] }. Необязательные параметры:
category — lashes или brows; limit — целое число от 1 до 100, по умолчанию 24.
Неизвестные и повторные параметры отклоняются с 400; недоступная база даёт 503.
Сортировка — sort_order, затем id. На главной запрашивается limit=8.

Таблица public.gallery_images хранит title, image_url, category, is_active,
sort_order и временные метки. RLS разрешает anon/authenticated только чтение
активных записей. Изменение URL, названия, порядка и видимости выполняется
в Supabase Table Editor; публичного редактирования нет.

Фотографии выбраны с Pexels по согласованию с владельцем проекта.
Это иллюстрации, а не работы Кристины; подпись блока сообщает об этом.
Ссылки на изображения находятся в seed, а не в компонентах. Для замены
достаточно изменить image_url соответствующей записи на HTTPS-ссылку

## Контакты и общий footer

HomeContacts завершает главную: CTA ведёт на /booking, контактная карточка
содержит каналы связи, адрес и режим работы. AppFooter находится в публичном
AppLayout и доступен на всех публичных страницах. Header и footer используют
общие StudioBrand и publicNavigationItems; ссылка «Контакты» ведёт на /#contacts
и работает при переходе с другой страницы.

Публичные редакционные данные находятся в src/features/studio/model/contacts.ts
и проверяются studioContactsSchema. Пока реальные данные не подтверждены,
значения равны null: интерфейс сообщает, что контакт уточняется,
и не создаёт ссылку на демонстрационный номер или аккаунт из Figma.

При заполнении:

- phone содержит internationalNumber в формате +<код страны><номер> и displayNumber для отображения;
- whatsappNumber — отдельный международный номер без пробелов; ссылка wa.me строится без плюса;
- telegramUsername и instagramUsername — имя аккаунта без @ и URL;
- location содержит city, address и directions — строки с пояснениями, как найти кабинет.

Телефон открывает tel:, социальные сети и WhatsApp — новую вкладку с
noopener noreferrer. Город в footer выводится только при заполненном location.
Контакты статические, поэтому дополнительных запросов API для них нет.
Реальные контактные данные необходимо добавить до production.

## Режим работы из Supabase

Таблица public.working_hours и GET /api/working-hours — общий источник
расписания для сайта и будущего Booking. API возвращает
{ data: WorkingDaySchedule[] } без параметров: id, dayOfWeek, startTime,
endTime и isWorkingDay. Время в ответе — HH:mm; поля базы — snake_case.
Неизвестные параметры дают 400, недоступная база — 503, запись через
этот маршрут не разрешена. Ответ не кэшируется сервером, клиентский кэш — 60 секунд.

Расписание редактируется в Supabase Table Editor:

- day_of_week: ISO-день недели, 1 — понедельник, 7 — воскресенье; один день — одна запись;
- рабочий день: is_working_day = true, start_time и end_time заданы с точностью до минуты;
- выходной: is_working_day = false, оба времени равны NULL;
- начало должно быть раньше окончания, интервалы через полночь не допускаются.

Для anon/authenticated разрешено только чтение с RLS. Редактирование посетителем
запрещено; права мастера добавляются на этапе Auth/Admin. Схема и ограничения
оформлены миграцией, начальное расписание не задано: нужно подтвердить реальные
дни и часы работы. До Booking также необходимо подтвердить часовой пояс кабинета.

WorkingHours показывает загрузку, ошибку с повтором и пустое состояние.
Соседние дни с одинаковыми часами объединяются. День без записи отображается
как «Уточняется», выходной — только при явном is_working_day = false.
Бизнес-контракт, запрос и хук находятся в features/workingHours;
серверное чтение и преобразование — в server/workingHours.

Проверки расписания:

```bash
pnpm supabase db query --linked --file supabase/tests/working-hours.sql
pnpm exec vitest run src/features/workingHours/model/groupWorkingHours.test.ts
```

SQL-проверка ограничений и RLS выполняется в транзакции с откатом.
Vitest проверяет порядок и объединение дней, различие выходных и незаполненных
дней, границу недели. Для desktop проверены 1024, 1280 и 1440px,
переходы из Header/footer, CTA записи, ошибка API и повтор запроса.
