# Kristina Kotova Booking

Персональный сайт Kristina Kotova Lash & Brow Studio с онлайн-записью.
Проект собирается поэтапно по ТЗ: публичный сайт, услуги и работы из базы,
запись и закрытый кабинет мастера.

## Стек

Next.js App Router, React, TypeScript, Ant Design, CSS Modules,
TanStack Query, Axios, React Hook Form и Zod. Для критичной бизнес-логики
предусмотрены Vitest и React Testing Library. База данных и авторизация мастера — Supabase.

## Локальный запуск

Нужны Node.js 24 LTS и pnpm 10.33.0 (версия закреплена в packageManager).

```bash
pnpm install --frozen-lockfile
pnpm dev
```

Сайт открывается на http://localhost:3000. Для услуг, галереи и расписания нужны настройки
Supabase из `.env.example`. Значения хранятся в `.env.local` и не попадают в Git.

```bash
pnpm lint
pnpm typecheck
pnpm build
pnpm start
```

## Архитектура

- `src/app` — маршруты, layout и Route Handlers. Страницы подключают views.
- `src/views` — композиция конкретных экранов.
- `src/components` — общие компоненты и публичный AppLayout.
- `src/features` — логика фич: model, api, hooks.
- `src/shared` — общая инфраструктура, включая Axios-клиенты и форматирование.
- `src/server` — серверные запросы и преобразование данных базы.
- `supabase` — конфигурация CLI, миграции и начальный каталог.
- `src/app/globals.css` — дизайн-токены; локальные стили — в CSS Modules.

Такое разделение повторяет принцип архитектурного референса,
а backend остаётся внутри Next.js.

## Каталог услуг и Supabase

Блок «Услуги» на главной получает активный каталог через Next.js API.
Начальные 6 услуг для ресниц и 4 услуги для бровей взяты из согласованного
макета Figma и находятся в `supabase/seed.sql`.

Для локального сайта создайте `.env.local` по примеру `.env.example`:

- `SUPABASE_URL` — URL облачного проекта.
- `SUPABASE_PUBLISHABLE_KEY` — publishable key из Settings → API Keys.

Переменные читает только серверный клиент. Для чтения каталога используется
Supabase Data API через Axios с ролью anon и защитой RLS; secret key и
service_role для этого не нужны. Без настроенного окружения API возвращает
503, а интерфейс предлагает повторить запрос. Подмены каталога статическими
данными нет.

`GET /api/services` возвращает `{ data: Service[] }`.
Параметр `category=lashes` или `category=brows` фильтрует категорию;
без параметра возвращаются обе. Неизвестные параметры, повторная category
и неизвестная категория возвращают 400. Цена передаётся числом в тенге,
длительность — в минутах. Поля API используют camelCase, таблица — snake_case.
API и политика RLS разрешают чтение только активных услуг. Посетители
не могут добавлять, изменять или удалять услуги.

`sortOrder` хранит порядок карточек. Изменения названий, цен, описаний,
длительности и активности в базе отображаются без изменения кода сайта.
Кэш TanStack Query сохраняет каталог категории на 60 секунд; следующий
запрос после устаревания кэша получает актуальные данные. Ответ API не
кэшируется сервером.

`ServiceCard` и `SectionHeading` — общие компоненты.
`ServicesCatalog` управляет выбранной категорией и состояниями запроса;
главная и ServicesView подключают общую фичу.
`features/services` содержит контракт, API-клиент и хук.
`server/services` содержит запрос базы, проверку ответа и преобразование
записи; Route Handler отвечает за HTTP и проверку параметров.
Ссылка карточки передаёт serviceId в /booking. ServiceCard использует h3
в секции главной и h2 на отдельной странице каталога. ID списка, к которому
относятся кнопки категорий, создаётся через useId.

### Выбор услуги в Booking

/booking разбирает serviceId через parseServiceSelectionRequest. Неверный
или повторный параметр показывает сообщение, неизвестная/неактивная услуга
не выбирается автоматически. BookingFlow загружает актуальный каталог через
GET /api/services. В первом шаге можно выбрать или изменить процедуру; ID
сохраняется в URL. Цена и длительность приходят из базы.

### Миграции

Версия Supabase CLI зафиксирована в devDependencies. Схема находится
в `supabase/migrations`; изменения схемы оформляются новой миграцией,
а не ручной правкой облачной таблицы.

```bash
pnpm supabase login
pnpm supabase link --project-ref YOUR_PROJECT_REF
pnpm supabase db push
pnpm supabase db query --linked --file supabase/seed.sql
```

Seed добавляет согласованный начальный каталог. Повторное применение
не перезаписывает уже существующие услуги: обновления каталога в MVP
делаются в Supabase Table Editor. Не меняйте id услуги — на него будет
ссылаться запись клиента. Отключение услуги делается через is_active.
Секреты, пароль базы и токен CLI не должны попадать в Git.

Проверка ограничений и RLS выполняется в транзакции с откатом,
поэтому тестовые записи не сохраняются:

```bash
pnpm supabase db query --linked --file supabase/tests/services.sql
```

## Режим работы из Supabase

Таблица public.working_hours и GET /api/working-hours — общий источник
расписания для сайта и Booking. API возвращает
{ data: WorkingDaySchedule[] } без параметров: id, dayOfWeek, startTime,
endTime и isWorkingDay. Время в ответе — HH:mm; поля базы — snake_case.
Неизвестные параметры дают 400, недоступная база — 503, запись через
этот маршрут не разрешена. Ответ не кэшируется сервером, клиентский кэш — 60 секунд.

Расписание редактируется в Supabase Table Editor:

- day_of_week: ISO-день недели, 1 — понедельник, 7 — воскресенье; один день — одна запись;
- рабочий день: is_working_day = true, start_time и end_time заданы с точностью до минуты;
- выходной: is_working_day = false, оба времени равны NULL;
- начало должно быть раньше окончания, интервалы через полночь не допускаются.

Для anon/authenticated разрешено только чтение с RLS. Редактирование посетителем
запрещено; доступ мастера проверяется через Supabase Auth и private.studio_owner. Схема и ограничения
оформлены миграциями. Подтверждённое расписание: ежедневно 10:00–20:00.
В booking_settings задан часовой пояс Asia/Almaty для Астаны.

WorkingHours показывает загрузку, ошибку с повтором и пустое состояние.
Соседние дни с одинаковыми часами объединяются. День без записи отображается
как «Уточняется», выходной — только при явном is_working_day = false.
Бизнес-контракт, запрос и хук находятся в features/workingHours;
серверное чтение и преобразование — в server/workingHours.

Проверки расписания:

```bash
pnpm supabase db query --linked --file supabase/tests/working-hours.sql
pnpm exec vitest run src/features/workingHours/model/groupWorkingHours.test.ts
```

SQL-проверка ограничений и RLS выполняется в транзакции с откатом.
Vitest проверяет порядок и объединение дней, различие выходных и незаполненных
дней, границу недели. Для desktop проверены 1024, 1280 и 1440px,
переходы из Header/footer, CTA записи, ошибка API и повтор запроса.

## Онлайн-запись

BookingFlow следует трём шагам макета: услуга → дата и время → контакты.
Имя и телефон проверяются React Hook Form + Zod. Даты выбираются кнопками
календаря Ant Design, время — слотами; ручного ввода нет. Ошибки загрузки
можно повторить. Выбор даты, времени и введённые контакты сохраняются при
возврате между шагами. После отправки показано сообщение из ТЗ и сводка.

Данные проходят через features/booking/api и TanStack Query. useBookingFlow
содержит состояние сценария и отправку, компоненты — отображение; views
компонуют страницу. Route Handlers валидируют HTTP-ввод, server/booking
вызывает ограниченные RPC Supabase и проверяет ответы Zod.

### API

- GET /api/booking/calendar: часовой пояс, сегодняшняя/последняя дата и рабочие часы.
- GET /api/booking/availability?serviceId=<uuid>&date=YYYY-MM-DD: дата и слоты с startTime, endTime, isAvailable.
- POST /api/bookings: serviceId, date, startTime, clientName, clientPhone, requestId.

POST принимает JSON, отклоняет неизвестные поля, некорректное имя/телефон,
чужой Origin и тело больше 4 КБ. Клиент не задаёт endTime, цену или статус.
База вычисляет окончание по актуальной длительности активной услуги;
новая заявка получает pending. В ответе — квитанция без имени и телефона.
Конфликт времени — 409, недоступная услуга — 404, ошибка ввода — 400,
недоступная база — 503 без внутренних подробностей. GET /api/bookings
не реализован: публичного списка клиентских данных нет.

### Расписание и целостность

В базе working_hours: каждый день 10:00–20:00. booking_settings содержит
time_zone = Asia/Almaty, шаг начала слотов 30 минут и окно записи 90 дней.
Период ограничен календарём и повторно проверяется базой. Сегодняшняя дата
и прошедшее время определяются по часам базы и часовому поясу студии,
а не по часовому поясу браузера. Часовой пояс для Астаны использует
[актуальное правило IANA UTC+5](https://www.iana.org/time-zones/releases/2024a).

RPC рассчитывает все варианты начала, которые помещаются в рабочий день.
Pending/confirmed/completed-заявки и blocked_slots занимают интервалы [start, end);
смежные записи разрешены. Отмена освобождает время. private.booking_occupancy
— технический индекс занятости, синхронизируемый триггерами; exclusion constraint
запрещает пересечение заявок и блокировок в одной транзакции, включая
параллельную отправку. При конфликте вся неудачная вставка откатывается.
Публичный доступ к таблицам заявок/блокировок и private-схеме закрыт.
Разрешены только RPC доступности и создания; функции имеют фиксированный
search_path. UI ручных блокировок относится к будущему этапу Admin.

requestId — UUID одной попытки: после обрыва связи повтор с теми же данными
вернёт ту же заявку. На время неопределённого результата контакты и возврат
заблокированы; повтор отправляется с прежним UUID. При подтверждённом
конфликте доступность обновляется и требуется выбрать другое время.
Цена/название услуги сохраняются в заявке как снимок на момент создания.

## Docker

Для запуска готовой версии сайта установите и запустите Docker Desktop
(или Docker Engine с Compose). Локальные Node.js и pnpm для контейнера не нужны.
Используется существующий облачный Supabase; миграции применяются отдельно
через CLI, контейнер не меняет схему базы при старте.

В корне должен быть заполненный `.env.local` с SUPABASE_URL и
SUPABASE_PUBLISHABLE_KEY из примера. Если этот файл уже настроен для pnpm dev,
он подходит и для Docker — менять его не нужно.

```bash
docker compose up --build --wait --wait-timeout 120
```

Сайт: http://localhost:3001. Порт привязан к 127.0.0.1 и доступен только
на этом компьютере. Запуск pnpm dev на 3000 может работать параллельно.
Если 3001 занят, выберите другой порт:

```bash
DOCKER_PORT=3002 docker compose up --build --wait --wait-timeout 120
```

```bash
docker compose ps
docker compose logs --tail 50 web
docker compose down
```

Dockerfile собирает Next.js на Node.js 24.21.0 LTS, устанавливает зависимости
по frozen lockfile и версии pnpm 10.33.0 из packageManager. Многоэтапная сборка
оставляет в рабочем образе standalone-сервер, public и .next/static.
Приложение работает от пользователя node; Compose init передаёт сигналы,
а остановка даёт серверу 20 секунд для завершения запросов.

NEXT_STANDALONE=true включается только на этапе сборки Docker. Обычные
pnpm dev, pnpm build и pnpm start сохраняют стандартный режим Next.js;
Vercel остаётся целевым production-размещением по ТЗ.

Healthcheck проверяет HTTP-ответ главной страницы. Статус healthy означает,
что сервер сайта отвечает; доступность Supabase проверяется отдельно через
каталог и календарь. При ошибке подключения интерфейс показывает повтор запроса.
Первой сборке нужен интернет для образа Node.js, зависимостей и Google Fonts.
После изменений исходников повторите команду запуска с --build.

### Окружение и ключи

.dockerignore разрешает передавать в сборку только исходники, public и файлы
конфигурации; все .env\* исключены, включая вложенные файлы. Dockerfile копирует
файлы явно. Ключи не передаются через ARG, ENV сборки или публичные переменные окружения:
Compose читает .env.local только при создании контейнера. Файл не монтируется
и не копируется в образ. .gitignore исключает окружение из Git; публикуется
только .env.example с пустыми примерами.

Не публикуйте вывод docker compose config без --quiet и полный docker inspect:
они могут показывать значения окружения запущенного контейнера.
Для изменения ключа обновите локальный файл и пересоздайте контейнер
командой docker compose up --force-recreate --wait.

Подробности формата сборки: [Next.js standalone](https://nextjs.org/docs/app/api-reference/config/next-config-js/output)
и [многоэтапная сборка Docker](https://docs.docker.com/build/building/multi-stage/).

## Вход мастера

/admin/login — форма email/пароля по макету; /admin — закрытый обзор заявок,
/admin/bookings — список записей с обработкой статусов. Публичный каталог
и онлайн-запись не требуют входа.

Supabase Auth работает через @supabase/ssr только на сервере. Используются
существующие SUPABASE_URL и SUPABASE_PUBLISHABLE_KEY; дополнительные секреты
и публичные переменные окружения не нужны. Cookie сессии имеет HttpOnly,
SameSite=Lax и Secure в production. На production-домене нужен HTTPS.
Пароль передаётся только сервису Auth при входе, не сохраняется в базе приложения
или локальном хранилище браузера. Автоматических повторов входа нет.

Proxy обновляет сессию и передаёт новые cookies в серверные компоненты и
ответ браузеру. Закрытый layout и API независимо проверяют пользователя через
getUser() и роль через is_studio_owner(). Cookie с ID, клиентские поля и
user_metadata не назначают права. Auth-ответы не кэшируются.

POST /api/auth/login принимает email/password, проверяет Origin и Host,
JSON, размер и схему; возвращает только профиль мастера, без токенов в JSON.
POST /api/auth/logout завершает текущую сессию, очищает cookies и перенаправляет
форму на вход. Другие устройства остаются в своих сессиях.
GET /api/me возвращает id/email назначенного мастера либо 401; изменение
пользователя через старый демо-PATCH удалено. Сбой Auth или базы не открывает
кабинет; интерфейс предлагает повторить запрос.

Миграция создаёт private.studio_owner и ограничивает кабинет одним Auth UUID.
Самостоятельная регистрация другого пользователя в Supabase не даёт права
мастера. Таблица ролей недоступна anon/authenticated напрямую; функция проверки
роли доступна только authenticated. Назначение выполняет владелец проекта.

Чтобы перенести кабинет на Кристину:

1. Создайте её пользователя в Supabase → Authentication → Users → Add user →
   Create new user. Она самостоятельно задаёт пароль. Подтвердите email.
2. Скопируйте UUID нового пользователя и выполните в SQL Editor от владельца
   проекта, заменив пример UUID фактическим значением:

```sql
begin;
update private.studio_owner
set user_id = 'UUID_НОВОГО_ПОЛЬЗОВАТЕЛЯ'::uuid
where singleton;
commit;
```

3. Войдите новым пользователем. У прежнего пользователя доступ к кабинету
   прекращается при следующей проверке роли; менять код или env не требуется.

UUID/email текущего владельца и пароль не включены в миграции, seed или Git.
Удаление пользователя в Supabase автоматически удаляет его назначение мастером.

Проверки: pnpm test, pnpm lint, pnpm typecheck и pnpm build.
SQL-проверка прав изолирована транзакцией и откатывает тестовые данные:

```bash
pnpm supabase db query --linked --file supabase/tests/auth.sql
```

Документация: [Supabase Auth для Next.js](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs),
[серверные сессии и кэширование](https://supabase.com/docs/guides/auth/server-side/advanced-guide),
[защита данных Next.js](https://nextjs.org/docs/app/guides/data-security).

## Кабинет и обработка записей

/admin показывает четыре карточки: новые, подтверждённые, выполненные и все
записи (включая отменённые). Под ними — пять последних pending-заявок и
пять ближайших pending/confirmed-записей, время окончания которых ещё не
прошло. Часовой пояс и сегодняшний день берутся из booking_settings в базе.
Карточки и секции ведут к полному списку; числа не заданы в коде.

/admin/bookings показывает клиента, телефон, услугу и цену на момент заявки,
дату, интервал, статус и доступные действия. Поиск работает по имени,
названию услуги и телефону; форматирование номера не мешает поиску.
Числа в названии вроде «2D / 3D» не превращаются в телефонный фильтр.
Есть фильтры статуса и даты. Параметры сохраняются в URL, страница содержит
20 строк, порядок — дата и начало по убыванию, затем UUID. Календарная дата
не сдвигается часовым поясом браузера. Пустой результат, загрузка,
недоступность сервиса и потеря доступа имеют отдельные состояния.

| Endpoint                              | Данные                                                 |
| ------------------------------------- | ------------------------------------------------------ |
| GET /api/admin/dashboard              | counts, newBookings, upcomingBookings, timeZone, today |
| GET /api/admin/bookings               | items, total, page, pageSize, timeZone                 |
| PATCH /api/admin/bookings/[id]/status | expectedStatus, status; возвращает обновлённую запись  |

Фильтры GET: page (от 1), status, date в YYYY-MM-DD, search (до 100 символов).
Неизвестные или повторные параметры отклоняются. PATCH проверяет UUID,
строгую схему, Origin/Host, JSON и размер. API проверяет настоящего мастера
до обращения к данным; ответы имеют private, no-store. Ни контакты, ни
RPC кабинета недоступны гостю или другому Auth-пользователю.

Переходы: pending → confirmed/cancelled, confirmed → completed/cancelled.
Каждое действие подтверждается в окне с клиентом, процедурой и временем.
Во время отправки повторные действия и закрытие окна недоступны.
У отменённых и выполненных заявок нет действий возврата. Автоматических
повторов изменения статуса нет; после ответа обновляются обзор, список
и доступность публичных слотов. Активные списки также обновляются каждые
30 секунд и при возвращении в окно; приватный кэш не сохраняется после
закрытия запроса или выхода.

В базе RPC повторно проверяют private.studio_owner. Прямые права на таблицу
bookings не расширены. change_booking_status блокирует строку, сверяет
expected_status и меняет статус в той же транзакции. Устаревшее действие
получает 409; ошибка остаётся в окне, даже если обновлённый список уже не
содержит строку. Триггер запрещает обратные переходы и при ручном SQL.
Отмена удаляет интервал из private.booking_occupancy; completed сохраняет
историю занятости. Проверка пересечений публичной записи продолжает работать.

features/adminBookings содержит контракт, Axios API, Query-хуки и компоненты;
views собирают обзор и таблицу, server/adminBookings выполняет защищённые
запросы. Правила переходов лежат в общей booking-модели. Supabase SDK с
сессией работает только на сервере; новых env-переменных и service_role нет.
Сущность blocked_slots и защита пересечений остаются действующими; отдельный
интерфейс ручных блокировок допускается будущим шагом по ТЗ.

Критичные проверки: 130 тестов проекта, включая статусы, HTTP-границы,
подтверждение действия, сохранение ошибки конфликта и обновление слотов;
lint, typecheck, build и Docker. SQL-проверка охватывает обзор, фильтры,
пагинацию, переходы, права и занятость в транзакции с откатом:

```bash
pnpm supabase db query --linked --file supabase/tests/admin-bookings.sql
```

В браузере проверены реальные действия через Supabase, конфликт двух
вкладок, фильтры и production-контейнер. Изолированные тестовые заявки
удалены после проверки. Публичная запись также проверена повторно в Docker.
